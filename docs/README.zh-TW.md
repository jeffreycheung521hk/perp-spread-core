# 繁體中文說明

這個專案把跨交易所價差研究中的「訂單簿 → 按數量計算成交金額 → 費用 → 淨價差判斷」抽成獨立 Rust 核心。第一個示範以 Hyperliquid 與 dYdX 的 SOL 永續合約為背景。

程式沒有交易所連線、私鑰或送單功能。它接收你提供的資料，完成可重現的計算。目前也沒有量測 Rust 相對 Python 的速度提升。

## 先跑範例

在 repo 根目錄執行：

```bash
cargo run --locked --offline -- --demo
```

範例使用刻意設計的合成報價。它展示訊號和損益計算，不能當成真實成交或歷史績效。

```bash
cargo test --locked --offline --all-targets
cargo build --locked --offline --release
python3 scripts/check_python_parity.py --binary target/release/spread-core
```

Rust 核心沒有第三方依賴；Python 對照程式也只使用標準函式庫。

## 核心怎樣工作

1. `OrderBook` 使用有序價格表。買入從最低賣價開始，賣出從最高買價開始；最多吃前 20 層，數量不夠就回傳錯誤。
2. 兩邊使用相同 SOL 數量。`Sizing::Auto { budget }` 按名義金額決定數量再向下取整；`Sizing::Fixed(quantity)` 不帶預算參數。已有倉位用獨立的 `quote_exit` 估平倉，只讀多倉的買盤、空倉的賣盤，不會被不用的入場側深度卡住。
3. `quote_pair` 分別計算多倉買入、空倉賣出、多倉賣出、空倉買回，共四筆成交和費用。
4. `assess` 扣除前一期 EMA 的退出價格成本、四筆費用及緩衝，再檢查報價新鮮度、兩邊接收時間差、買賣差價與吃單滑價。
5. `paper_open().mark_close(&exit)` 接收不可改寫的 `ExitQuote`，估算一組已完整成交部位的損益。`Quote`、`ExitQuote` 與 `Fill` 都只提供 getter，呼叫端不能改數量或成交金額來繞過檢查。

數字以「單邊參考名義本金」作 bps 分母。1 bp = 0.01%。使用雙邊合計本金計算時，回報率約為單邊口徑的一半。

## 如何避免數字失真

- 價格、數量各保留六位小數；美元保留十二位；bps 保留六位。
- 金額使用 `i128` 固定精度整數，延續原 Python `Decimal` 避免二進位浮點誤差的原則。
- 計算保留逐層成交總金額；VWAP 只格式化作顯示，不會先四捨五入平均價再拿去算費用。
- 四筆費用按各自成交金額計算；平倉時可帶入當時不同的費率。
- 正向價差向下取整，費用和預估成本向上取整。EMA 有微小固定精度近似，不代表完整狀態與 Python 逐位相同。
- 非法數字、超出精度、溢位、訂單簿交叉、深度不足及倒序更新都有明確錯誤。

## 目前能證明甚麼

Rust 測試驗證計算及錯誤行為。另有固定種子的合成案例，以獨立 Python `Decimal` 計算對照 VWAP、四筆費用、淨價差、篩選結果和即時往返損益。對照的是數學核心，不是整個 Python 模擬交易引擎。

訂單簿交叉時會保留深度並繼續接收增量，只暫停報價。有效 snapshot 開始新的序號範圍；重複或較舊 delta 會被忽略，不會刷新接收時間。來源與接收時間的 watermark 會跨過 snapshot 和 `invalidate()` 保留；adapter 仍須隔離不同連線的訊息及檢查缺口。

EMA 必須依幣種、交易方向和數量政策分開維護；小 alpha 的逐步向上取整仍可能卡住。`received_ms` 是最後一則有效訂單簿事件的接收時間，不是連線健康狀態。不要僅為避免 stale 而從一般網路 ping 製造空 delta。預設時間門檻也尚未按兩個交易所的實際 feed 頻率校準。

還需要另外完成交易所接線、資料缺口檢查、兩腿獨立／部分成交、funding、保證金及資金帳本，才適合驗證實盤。請依帳戶與交易所規格核實費率、數量步長及合約單位；範例參數不是實際費率或建倉建議。這次優先處理審查 #1–#4，其餘項目列在 [後續清單](REVIEW_FOLLOWUPS.md)。

程式已放在 repo 根目錄，後續可逐步新增 Python 收集器介面與實際成交比較，不必先重寫所有分析流程。
